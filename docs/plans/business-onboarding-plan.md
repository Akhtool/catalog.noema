# План: онбординг и вход для бизнеса

## Для команды: как открыть страницу онбординга

Страница онбординга **не открывается по простой ссылке** `/onboarding` — без ключа будет редирект на вход.

**Открывать только так (подставьте свой ключ из env):**
- Локально: `http://localhost:3000/onboarding?key=ВАШ_КЛЮЧ`
- Прод: `https://catlg.ru/onboarding?key=ВАШ_КЛЮЧ`

Ключ задаётся в переменной окружения `ONBOARDING_ACCESS_KEY`. Сохраните полную ссылку в закладках.

---

## 1. Модель работы

- **Бизнес подключается к каталогу** по запросу. Команда создаёт для него витрину (поддомен, страница), учётную запись владельца и передаёт бизнесу данные для входа.
- **Бизнес не регистрируется сам.** Он получает от команды документ с ссылкой вида `[название].catlg.ru/login` и логин/пароль, входит и управляет каталогом в админке.
- **Онбординг и signup** остаются в продукте **только для внутреннего использования командой**: удобно регистрировать новый бизнес и владельца без ручного ввода в Supabase. Бизнес эти страницы не видит и не использует.

---

## 2. Сценарии

### 2.1 Команда регистрирует новый бизнес

1. Команда открывает `/onboarding` (или `/signup` → редирект на `/onboarding`) на корневом домене (например `catlg.ru` или `localhost`).
2. **Шаг 1 — регистрация пользователя** (если не авторизован): email, пароль (min 6), имя (необязательно). После успеха — переход на шаг 2 без перезагрузки.
3. **Шаг 2 — создание бизнеса**: название, slug (опционально). После успеха — редирект на каталог `{slug}.catlg.ru` (можно сразу проверить витрину).
4. Команда отправляет бизнесу документ: ссылка `https://[slug].catlg.ru/login`, логин (email) и пароль для входа.

Вариант: авторизованный сотрудник без привязанного бизнеса открывает `/onboarding` — видит сразу шаг «Создание бизнеса». Если у пользователя уже есть бизнес — редирект в его каталог.

### 2.2 Бизнес входит в админку

1. Бизнес получает от команды ссылку и учётные данные.
2. Открывает `https://[slug].catlg.ru/login` (или `https://catlg.ru/login` и затем попадает на свой каталог после входа).
3. Вводит только **логин (email) и пароль**. Никаких ссылок на регистрацию или онбординг на странице входа нет.

---

## 3. Маршруты

| Маршрут | Кто использует | Поведение |
|--------|-----------------|-----------|
| `/login` | Бизнес (и команда) | Только форма входа: email + пароль. **Без ссылки** «Регистрировать бизнес» / «Нет аккаунта?». |
| `/onboarding` | Только команда | Регистрация пользователя (если не авторизован) + создание бизнеса. Не рекламируется и не ссылается с `/login`. |
| `/signup` | Только команда | Редирект на `/onboarding` для единой точки входа. |
| `/admin/business/new` | Команда / авторизованные | Создание второго бизнеса и т.п. (как сейчас). |

**Middleware:** `/onboarding`, `/login`, `/signup` остаются в matcher исключений (не перехватываются поддоменным rewrite).

## 4. Что нужно сделать (план реализации)

### Этап 1. Убрать публичную ссылку на регистрацию с логина

- **Файл:** `app/login/login-form.tsx`
- **Действие:** Удалить блок с ссылкой «Нет аккаунта? Зарегистрировать бизнес» → `/onboarding`. Страница входа должна содержать только форму логин/пароль и кнопку «Войти» (и при необходимости «Войти по ссылке» и т.п., если они есть).
- **Результат:** Бизнес на странице входа не видит способа зарегистрироваться; вход только по выданным учётным данным.

### Этап 2. Документация продукта

- **Файл:** `docs/reference/product-contract.md`
- **Действие:** Обновить раздел «Онбординг бизнеса» (или эквивалент):
  - Бизнес **не регистрируется сам**. Подключение каталога и выдача учётных данных — зона ответственности команды.
  - Маршрут `/onboarding` (и переход с `/signup`) — **внутренний инструмент команды** для регистрации нового бизнеса и владельца без ручного ввода в Supabase.
  - Для бизнеса: единственная точка входа в админку — страница входа по логину и паролю (без ссылки на регистрацию).

### Этап 3. Защита /onboarding (опционально)

Реализована **защита по секретному ключу в URL**. Остальные варианты — ниже.

## 5. Варианты защиты /onboarding

| Вариант | Описание | Плюсы | Минусы |
|--------|----------|--------|--------|
| **1. Без защиты** | Доступен всем, кто знает URL. Ссылок с сайта нет. | Простота, команда хранит ссылку в закладках. | Случайный переход или перебор URL даёт доступ. |
| **2. Query-ключ** ✅ реализовано | В `.env`: `ONBOARDING_ACCESS_KEY=секретная_строка`. Вход только по `/onboarding?key=секретная_строка`. Иначе редирект на `/login`. | Просто, не нужен отдельный логин; ключ можно передать внутри команды. | Ключ виден в URL (история, логи); один скомпрометированный ключ на всех. |
| **3. IP-список** | На сервере (middleware или page) проверять `request.headers.get('x-forwarded-for')` / `request.ip` против списка разрешённых IP (env или конфиг). При несовпадении — 404 или редирект. | Скрывает онбординг от посторонних без знания ключа. | Нужен стабильный IP офиса/VPN; сложнее при удалёнке и смене провайдера. |
| **4. Basic Auth** | Поднять перед Next.js (nginx или веб-сервер хостинга) HTTP Basic Auth на путь `/onboarding`. Логин/пароль только для команды. | Стандартный механизм, не в коде приложения. | Настройка на уровне хостинга; отдельные учётные данные. |
| **5. Отдельный внутренний домен** | Раздавать онбординг только с `admin.catlg.ru` или `internal.catlg.ru`, основной сайт — `catlg.ru`. На основном домене `/onboarding` отдаёт 404. | Чёткое разделение «внутреннее / публичное». | Нужна настройка DNS и роутинга. |

**Рекомендация:** для MVP достаточно варианта 2 (query-ключ): задать `ONBOARDING_ACCESS_KEY` в переменных окружения на хостинге (или в `.env` локально) и открывать онбординг только по ссылке с ключом. Команда сохраняет в закладках полную ссылку `https://catlg.ru/onboarding?key=...`. При включённой защите использовать именно эту ссылку (редирект с `/signup` не передаёт ключ).

```
ONBOARDING_ACCESS_KEY=ваш_секретный_ключ
```
