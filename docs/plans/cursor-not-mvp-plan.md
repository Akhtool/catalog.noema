# План вывода проекта из MVP через Cursor

## Зачем этот документ

Этот план написан под реальный сценарий:

- проект развивается через Cursor и нейросети;
- код в основном пишешь не ты руками;
- твоя задача не "стать программистом за неделю", а научиться управлять качеством проекта;
- цель: довести `catalog.noema` до состояния, где это уже не просто MVP, а поддерживаемый продукт.

Главная мысль:

> Тебе нужно не больше генерации кода, а больше контроля над тем, что генерируется.

---

## Что значит "не MVP" для этого проекта

Проект можно считать вышедшим из стадии MVP, когда:

- онбординг бизнеса проходит без ручной помощи;
- публичный каталог стабильно работает для реальных пользователей;
- критические сценарии защищены тестами;
- доступы и изоляция бизнесов проверены;
- в коде нет опасных временных решений;
- архитектура достаточно понятна, чтобы новые фичи не ломали старые;
- у тебя есть метрики использования, а не только ощущения;
- продуктом пользуются регулярно, а не только в рамках теста.

---

## Как работать через Cursor правильно

Тебе не нужно просить Cursor: "сделай красиво", "улучши архитектуру", "перепиши по уму".

Так он почти всегда даст либо хаос, либо лишние абстракции.

Правильный режим работы:

1. Даёшь Cursor очень узкую задачу.
2. Даёшь контекст, зачем это нужно.
3. Ограничиваешь, что менять можно, а что нельзя.
4. Просишь сначала анализ, потом изменение.
5. После каждого крупного шага проверяешь результат через `lint`, `typecheck`, `build`, тесты.

Полезный шаблон промпта:

```text
Контекст:
- Это Next.js + Supabase проект.
- Кодовую базу нужно улучшать без лишних абстракций.
- Нельзя делать большие хаотичные рефакторы.

Задача:
- Выполни только <одна конкретная задача>.

Ограничения:
- Сначала коротко опиши план.
- Не меняй unrelated файлы.
- Не добавляй абстракции "на будущее".
- Сохрани текущее поведение, если не сказано иначе.

Проверка:
- После изменений покажи, какие файлы изменены.
- Скажи, какие риски остались.
```

## Общая стратегия

Работу нужно вести в таком порядке:

1. Убрать риски безопасности и опасные временные решения.
2. Зафиксировать базовый инженерный контроль.
3. Покрыть тестами критический поток.
4. Сделать архитектуру понятной.
5. Разрезать самые тяжёлые файлы.
6. Централизовать доступы и бизнес-правила.
7. Стабилизировать онбординг и ежедневное использование.
8. Добавить наблюдаемость и процесс релиза.

Не надо начинать с "идеальной архитектуры".

Сначала проект должен стать безопасным и предсказуемым.

## Этап 1. Закрыть опасные места

### Цель

Убрать вещи, которые могут привести к утечке данных, поломке логики или несанкционированному доступу.

### Что сделать

1. Удалить или жёстко закрыть `app/temp/slugs/page.tsx`.
2. Проверить client-side код, который напрямую пишет в Supabase.
3. Проверить RLS-политики и server-side доступы.
4. Проверить, что `service_role` не используется в клиентском коде.
5. Проверить tenant isolation: один бизнес не должен получать доступ к данным другого.

### Почему это важно

Пока в проекте есть временные обходные пути, продукт нельзя считать взрослым.  
Он может выглядеть рабочим, но оставаться хрупким и опасным.

### Что просить у Cursor

#### Задача 1: найти опасные точки доступа

```text
Проведи аудит проекта на предмет опасных client-side обращений к Supabase.

Что нужно найти:
- прямые insert/update/delete из client components;
- временные страницы или служебные маршруты;
- места, где безопасность держится только на UI, а не на серверной проверке;
- возможные нарушения tenant isolation.

Покажи результат в виде списка:
- файл
- что именно опасно
- насколько это критично
- что нужно сделать

Ничего не меняй, только аудит.
```

#### Задача 2: закрыть временный маршрут

```text
Нужно устранить риск, связанный со страницей `app/temp/slugs/page.tsx`.

Требования:
- если маршрут не нужен продукту, удали его полностью;
- если нужен только для разработки, он не должен быть доступен в production;
- никаких прямых операций с таблицами `business`, `category`, `product` из client-side быть не должно;
- не ограничивайся скрытием кнопки или ссылки, защита должна быть реальной.

Сначала коротко скажи, какой вариант выбираешь.
Потом внеси изменения.
В конце покажи список файлов и коротко объясни результат.
```

### Критерий готовности этапа

- нет временных маршрутов с доступом к данным;
- опасные client-side операции убраны или перенесены на сервер;
- логика доступа не держится только на интерфейсе.

## Этап 2. Ввести обязательный технический минимум

### Цель

Перестать принимать изменения "на глаз".

### Что сделать

1. Добавить `typecheck` в `package.json`.
2. Зафиксировать обязательный набор проверок:
   - `npm run lint`
   - `npm run typecheck`
   - `npm run build`
3. Создать короткий чеклист релиза.
4. Не принимать ни одну серьёзную правку без этих проверок.

### Почему это важно

Cursor может генерировать код, который выглядит нормально, но ломается на типах, сборке или скрытых зависимостях.

### Что просить у Cursor

```text
Добавь базовый инженерный контроль для проекта.

Задача:
- проверь текущие scripts в `package.json`;
- добавь `typecheck`, если его нет;
- создай короткий `docs/checklists/release-checklist.md` с обязательными шагами перед релизом;
- не меняй ничего лишнего.

Требования:
- минимализм;
- без лишних CI-инструментов на этом шаге;
- итог должен быть пригоден для ежедневного использования.
```

### Критерий готовности этапа

- есть `typecheck`;
- есть понятный локальный release checklist;
- техническая проверка стала обязательной привычкой.

## Этап 3. Покрыть тестами критический поток

### Цель

Защитить основной продуктовый сценарий от поломок.

### Что считать критическим потоком

#### Со стороны бизнеса

1. Войти в систему.
2. Создать или отредактировать бизнес.
3. Добавить категории и товары.
4. Получить рабочий публичный каталог.

#### Со стороны клиента

1. Открыть каталог.
2. Найти товар.
3. Добавить его в корзину.
4. Оформить заказ.
5. Уйти в WhatsApp / Telegram / звонок.

### Что сделать

Сначала добавить 5-10 тестов только на эти сценарии.

Не надо сразу покрывать всё приложение.

### Что просить у Cursor

```text
Нужно добавить минимальный набор тестов на критический пользовательский поток.

Контекст:
- это не enterprise-проект;
- не нужен огромный test suite;
- нужно защитить только самые важные сценарии.

Сделай так:
- предложи подходящий минимальный стек тестирования для этого проекта;
- выбери 5-10 тестов с максимальной пользой;
- сначала покажи список тест-кейсов;
- потом реализуй их без лишней инфраструктуры.

Приоритет:
- публичный каталог
- корзина
- оформление заказа
- доступ к админке
```

### Критерий готовности этапа

- есть автоматическая проверка критического потока;
- после каждой крупной правки можно быстро проверить, что продукт не развалился.

## Этап 4. Зафиксировать архитектуру

### Цель

Сделать так, чтобы ты, Cursor и будущие изменения опирались на одну и ту же модель проекта.

### Что должно быть описано

Создай `docs/architecture/architecture.md`, где коротко зафиксировано:

- какие есть сущности;
- что хранится в БД;
- что client-side;
- что server-side;
- где бизнес-логика;
- где data access;
- где проверки доступа;
- какие правила нельзя нарушать.

### Базовые правила, которые стоит зафиксировать

- `components` отвечают за UI;
- `store` отвечает за клиентское состояние;
- `lib` содержит чистую бизнес-логику и утилиты;
- `app/*/actions.ts` отвечает за server-side действия;
- доступ к данным чужого бизнеса невозможен;
- временные и отладочные сценарии не живут в production-маршрутах.

### Что просить у Cursor

```text
Нужно создать `docs/architecture/architecture.md` по текущему проекту.

Требования:
- документ должен быть коротким и практичным;
- без академической воды;
- он должен описывать текущую архитектуру, а не выдуманную идеальную;
- отдельно зафиксируй инварианты, которые нельзя ломать.

Сначала проанализируй проект.
Потом создай документ.
```

### Критерий готовности этапа

- появился один основной архитектурный документ;
- Cursor получает более точный контекст для следующих задач.

## Этап 5. Разрезать самые тяжёлые файлы

### Цель

Убрать файлы, которыми страшно управлять.

### Приоритетные файлы

На момент составления плана особенно подозрительны:

- `components/business/business-profile-editor-sheet.tsx`
- `app/admin/product/actions.ts`
- `app/admin/business/actions.ts`

### Почему это важно

Большие файлы в AI-проекте почти всегда означают:

- смешение обязанностей;
- плохую читаемость;
- сложность в отладке;
- высокий риск случайных поломок.

### Как резать правильно

Делить надо не "на куски", а по ролям:

- validation
- access checks
- queries
- upload logic
- mapping / transform logic
- UI sections

### Что просить у Cursor

```text
Нужно декомпозировать крупный файл без изменения поведения.

Файл: <вставь путь>

Требования:
- сначала проанализируй, какие ответственности смешаны;
- предложи разбиение на модули по ролям;
- не делай большой абстрактный рефакторинг;
- не меняй поведение;
- после разбиения код должен стать проще читать и поддерживать.

Сначала покажи план декомпозиции.
Потом внеси изменения.
В конце покажи, какие части куда вынесены.
```

### Критерий готовности этапа

- самые тяжёлые файлы стали заметно меньше;
- в них стало легче ориентироваться;
- бизнес-логика, доступы и UI не перемешаны.

## Этап 6. Централизовать доступы и проверки

### Цель

Убрать размазанную security-логику и снизить риск несогласованного поведения.

### Что сделать

Свести в один слой:

- проверку доступа пользователя к бизнесу;
- получение текущего `businessId`;
- проверки владения товаром / категорией / брендом;
- общие guard-функции для server-side действий.

### Почему это важно

Если одинаковая проверка написана в 5 местах, Cursor рано или поздно сломает 1 из них.

### Что просить у Cursor

```text
Нужно провести рефакторинг access-control логики.

Задача:
- найти повторяющиеся проверки доступа в server actions;
- вынести их в один понятный модуль;
- не менять продуктовое поведение;
- сохранить явность, не прятать всё в магию.

Результат должен дать:
- меньше дублирования;
- единые правила доступа;
- более безопасную поддержку проекта.
```

### Критерий готовности этапа

- доступы проверяются единообразно;
- меньше копипасты;
- безопасность перестаёт быть случайным свойством отдельных файлов.

## Как оценивать прогресс

Смотри не на количество изменённых файлов, а на такие вопросы:

- стало ли безопаснее?
- стало ли проще выпускать изменения?
- стало ли легче понимать код?
- можно ли проверять качество автоматически?
- может ли новый бизнес пройти путь без твоей помощи?
- знаешь ли ты, что реально делают пользователи?

Если на эти вопросы ответы всё чаще "да", значит проект реально выходит из MVP.

---

## Чего не делать

- не запускать большие хаотичные рефакторы;
- не просить Cursor "улучшить архитектуру целиком";
- не добавлять сложные абстракции без конкретной причины;
- не строить enterprise-систему раньше времени;
- не путать "много новых фич" с взрослением продукта.

---

## Финальная цель

Цель не в том, чтобы код стал "идеальным".

Цель в том, чтобы:

- проект был безопасным;
- изменения были предсказуемыми;
- продукт можно было поддерживать;
- новые пользователи могли проходить путь самостоятельно;
- ты управлял проектом, а не Cursor управлял тобой.
